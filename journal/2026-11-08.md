## Ce que j'ai compris
- Git ≠ GitHub : l'outil d'historique d'un côté, le site qui l'héberge de l'autre.
- Un dépôt = un projet : le code du budget (privé) est séparé de mes notes (public, portfolio).
- Un dépôt doit être créé vide sur GitHub si on a déjà un historique local, sinon les deux historiques entrent en conflit.
- Une GitHub App reçoit des droits précis sur des dépôts choisis : c'est le principe du moindre privilège.
- On distingue **production** (la version utilisée avec les vraies données) et **développement** (une copie qu'on peut casser sans risque).
- **Tester avant de livrer** révèle des bugs qu'on n'aurait jamais vus à l'œil (le debounce perdu au rechargement).
- Le localStorage garde les données dans un seul navigateur : pour un couple et pour l'IA, il faudra un **serveur** (backend), avec des comptes et une clé d'API cachée.
- **On ne commence pas par l'écran mais par le besoin** : discovery → user stories → priorisation → maquette → code.
- Une maquette se change en 10 minutes, du code en des heures : on valide les parcours avant de coder.
- Un libellé mal choisi (« à affecter ») suffit à rendre une fonction incompréhensible : c'est le **UX writing**.
- Trop de fonctions tue l'usage : la **gestion par exception** (ne montrer que ce qui demande une décision) rend un outil supportable au quotidien.
- Un benchmark sert à confirmer ses choix, emprunter les bonnes idées et trouver ce qui nous différencie.
